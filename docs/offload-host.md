# Offload host

The `offload` inventory alias is a Mac on the LAN that another person owns and
uses. Planwright work is dispatched to it from the Linux host (`server`) over
SSH, only when the operator says the Mac is free; deciding that automatically
(from keyboard and mouse idle time) can come later.

## Posture

- **A dedicated account.** Work runs in its own macOS account
  (`osx_offload_user`, default `fleet`), never the owner's, so it cannot read
  her files, browser or keychain. It is a standard account, not an
  administrator: an administrator can write the admin-group Homebrew prefix
  and `/Applications` without sudo, so whoever held `server`'s key could
  replace programs the owner runs. The play refuses an administrator account,
  and refuses to configure the host from any other account, reading both from
  the process rather than `USER`. Nothing it does asks for sudo: tools come
  from mise in the account's home, the owner's Homebrew is used read-only and
  never written to, the login shell is left as is, and the one root step, the
  sshd hardening, is an administrator's (below). The GitHub MCP sync is
  skipped there, as on `server`, since its token lives in a personal
  1Password item the host's read-only service account cannot read.
- **One key, from one address.** `server` holds an on-disk ed25519 key,
  `~/.ssh/id_offload` (`roles/ssh`), generated by the playbook and never
  committed. It lives on disk because an unattended session cannot approve a
  1Password agent prompt. The Mac trusts it through
  `~/.ssh/authorized_keys.offload`, rendered from 1Password by
  `scripts/op-render.sh`, which restricts it to `server`'s address (`from=`)
  and grants a login session with a terminal and no forwarding
  (`restrict,pty`: no agent, X11 or port forwarding); any command still runs.
  The account's own `~/.ssh/authorized_keys` stays unmanaged, so a shell in
  the account can add a key there with no address pin; managing that file
  instead would risk locking the account out over a bad render.
- **No password login.** `roles/osx/files/sshd/050-dotfiles-hardening.conf`
  turns off password and keyboard-interactive login and root login for every
  account on the Mac, the owner's included. An administrator installs it with
  `scripts/offload-sshd-harden.sh`, run as root from a checkout of their own
  (root running the work account's clone would hand that account root). The
  script refuses unless the rendered authorized key is in place, asserts the
  effective `sshd -T` values as a connection from the `from=` address would
  get them, and removes the drop-in again if that check fails where none was
  installed before; one that replaced an earlier drop-in is kept, and the
  script says so. The play, which cannot read sshd's effective config
  without root, reports when the drop-in is missing and fails when it
  differs from the tracked one.
  Remote Login must stay on; the play fails if it is off rather than touching
  it.
- **What is not checked.** Nothing compares `from=` with the address the
  connection really arrives from; a working key login from `server` is the
  proof.
- **The owner's administrators are trusted.** The separation runs one way:
  an administrator on the Mac can read everything the work account holds,
  its service-account token, its signing and GitHub keys and its gh token
  included.

## The 1Password LAN item

`dotfiles-lan-ssh` (vault `Dotfiles Service Account`) gains these fields beside
the ones in [roles/ssh/README.md](../roles/ssh/README.md):

| Field | Holds |
|---|---|
| `offload_alias` | short ssh alias for the Mac |
| `offload_host` | its resolvable hostname |
| `offload_user` | the work account; must equal `osx_offload_user` |
| `offload_client_pubkey` | `server`'s `~/.ssh/id_offload.pub` |

`server_ip` is reused as the `from=` address. If `server`'s address changes,
update that field and re-run the playbook on the Mac at its console, logged in
as `fleet`: with password login off, the key trusted only from the old address
was the one way in over SSH. To revoke the key, delete
`~/.ssh/authorized_keys.offload` there the same way; emptying
`offload_client_pubkey` does not, since the render refuses an empty field and
leaves the old file in place. Every host renders the alias block, so
`offload_alias`, `offload_host` and `offload_user` must exist before any
host's next playbook run, or its LAN alias sync fails.

## One-time setup

In order; each step needs a person, except the playbook run on `server`.

1. **Add the fields** (on `server`, with a writable 1Password account):

   ```fish
   set -lx OP_ACCOUNT (cat ~/.config/dotfiles/op-account)
   op item edit dotfiles-lan-ssh --vault 'Dotfiles Service Account' \
       'offload_alias[text]=<alias>' 'offload_host[text]=<mac-hostname>' \
       'offload_user[text]=fleet'
   ```

2. **Create the work account** as a standard account, on the Mac in an
   administrator's session (zsh), with the owner typing her administrator
   password:

   ```zsh
   sudo sysadminctl -addUser fleet -fullName Fleet -password - -adminUser <owner-account> -adminPassword -
   ```

   An account created as an administrator earlier is made standard the same
   way, then checked (the second line prints nothing once it is standard):

   ```zsh
   sudo dseditgroup -o edit -d fleet -t user admin
   id -Gn fleet | tr ' ' '\n' | grep -x admin
   ```

   Steps 4, 5 and 7 reach the account over SSH, so Remote Login must be on
   (System Settings, General, Sharing). If it allows only listed users, add
   the account too:
   `sudo dseditgroup -o edit -a fleet -t user com.apple.access_ssh`.

3. **Run the playbook on `server`**, which mints `~/.ssh/id_offload`, then
   store its public half:

   ```fish
   set -lx OP_ACCOUNT (cat ~/.config/dotfiles/op-account)
   op item edit dotfiles-lan-ssh --vault 'Dotfiles Service Account' \
       'offload_client_pubkey[text]='(cat ~/.ssh/id_offload.pub)
   ```

4. **Give the Mac its own service account**, written straight into the work
   account over the one password login (the token never reaches a terminal):

   ```fish
   begin
       set -lx OP_ACCOUNT (cat ~/.config/dotfiles/op-account)
       op service-account create dotfiles-offload --vault 'Dotfiles Service Account:read_items' --raw
   end | ssh -o PubkeyAuthentication=no <alias> 'umask 077; mkdir -p ~/.config/dotfiles; cat > ~/.config/dotfiles/op-service-account-token'
   ```

5. **Bootstrap the work account**, over `ssh <alias>`, in its zsh. No sudo
   is involved: mise installs the pinned tools of
   `roles/osx/files/mise-offload/offload.toml` into the account's home,
   ansible among them, and the playbook installs nothing with the owner's
   Homebrew, using her `brew`, `fish` and `op` read-only:

   ```zsh
   export PATH="$HOME/.local/bin:$HOME/.local/share/mise/shims:/opt/homebrew/bin:$PATH"
   command -v mise >/dev/null || curl -fsSL https://mise.run | sh
   test -d ~/dev/dotfiles || git clone https://github.com/inkatze/dotfiles.git ~/dev/dotfiles
   mkdir -p ~/.config/mise/conf.d ~/.config/dotfiles
   ln -sfn ~/dev/dotfiles/roles/osx/files/mise-offload/offload.toml ~/.config/mise/conf.d/offload.toml
   echo offload > ~/.config/dotfiles/host
   cd ~ && mise install uv && mise install
   ansible-galaxy collection install community.general
   for t in brew op jq mise fish tmux gh git ansible-playbook; do command -v "$t" >/dev/null || echo "missing: $t"; done
   cd ~/dev/dotfiles && ./scripts/playbook.sh
   ```

   A `missing:` line names a tool to add before the run: `brew`, `fish` and
   `op` from the owner's account, `git` from the Command Line Tools,
   anything else with mise. The play also refuses, before its Homebrew and
   macOS tasks, while one of `osx_offload_required_tools` is missing. The run
   renders the key the next step needs and keeps the same `PATH` for later
   sessions in `~/.zshenv`; password login stays on until step 6.

6. **Close password login**, in an administrator's session on the Mac (zsh),
   once step 5's run has rendered the key. The clone is the administrator's
   own, never the work account's:

   ```zsh
   d="$(mktemp -d)" && git clone --depth 1 https://github.com/inkatze/dotfiles.git "$d/dotfiles" && sudo "$d/dotfiles/scripts/offload-sshd-harden.sh" fleet; rm -rf "$d"
   ```

   One line on purpose: the clone goes into a fresh directory only the
   administrator can write, and `sudo` runs only if that clone succeeded, so
   root never runs a path the work account could have created first.

   It prints `CHANGED` once installed. From then on `ssh <alias>` works only
   with the key, and the playbook fails if the installed drop-in ever stops
   matching the tracked one, which an administrator fixes by re-running this.

7. **Sign the work account in**, over `ssh <alias>`, all to the operator's
   second Claude account and its GitHub identity; nothing here stores these
   credentials. The session is the account's zsh, where an interactive `#`
   starts no comment, so `/login` with the second account is typed inside
   `claude`:

   ```zsh
   security unlock-keychain ~/Library/Keychains/login.keychain-db
   claude
   gh auth login --insecure-storage --scopes admin:public_key,admin:ssh_signing_key
   gh ssh-key add ~/.ssh/id_github_auth.pub --type authentication --title 'dotfiles offload auth'
   gh ssh-key add ~/.ssh/id_signing.pub --type signing --title 'dotfiles offload signing'
   gh auth refresh --remove-scopes admin:public_key,admin:ssh_signing_key
   ```

   The last line drops the key-admin scopes once the keys are added, since
   the token sits in a plain file that anyone with this account's shell can
   read. Claude Code keeps its login in the account's keychain, which an SSH
   session does not unlock by itself: after a reboot, run the
   `security unlock-keychain` line again before dispatching. Add
   `~/.ssh/id_signing.pub` to `roles/ssh/files/allowed_signers` in a
   follow-up commit so local signature checks pass.

## GitHub Actions runners

The play (`roles/osx/tasks/offload-runner.yml`) turns the work account into a
self-hosted runner for the repositories in `osx_runner_repos`, plus any
`owner/repo` lines in `~/.config/dotfiles/runner-repos` (private names stay
out of the repo). One runner per repository, each in
`~/actions-runners/<owner>-<repo>`, labelled `self-hosted`, `macOS`,
`mac-fleet`, each kept running by the work account's own crontab at `nice 10`.
The account only logs in over ssh, so it has no launchd user domain (`gui/` and
`user/` bootstraps both fail) and no sudo for a LaunchDaemon. Nothing uses
sudo or Homebrew. The release is pinned with its published sha256 in the role
defaults; bump both together.

- **Keeping it running.** Per repository the play adds an `@reboot` crontab
  line and one every `osx_runner_recheck_minutes` (default 5), both calling
  `runner-start.sh`, and runs it once itself. That script starts
  `runner-gate.sh` detached and niced (a pid file in `~/.cache` names the
  running copy) and does nothing when it already runs, so a re-check never
  disturbs a job. The gate outlives the cron job and any ssh session. The
  crontab lines carry no `%`, which cron reads as a newline. To stop a runner,
  kill the pid in `~/.cache/dotfiles-runner-<owner>-<repo>.pid` and remove its
  two `dotfiles runner` lines from `crontab -e`.
- **Yielding.** `runner-gate.sh` starts the runner in `--once` mode, only while
  the keyboard and mouse have been still for `osx_runner_idle_seconds` and the
  one-minute load average is under `osx_runner_load_max` (default 6). Whichever
  account owns the console does not matter: a Mac left untouched and lightly
  loaded serves jobs, one in use or busy does not. When the
  Mac is in use and no job has started it stops the listener (the runner shows
  offline). A job already running is never interrupted: it finishes niced and
  nothing new starts. A job assigned in the instant the owner returns can be
  dropped by GitHub as a lost runner; re-run it.
- **Registration.** The play fetches a registration token with the work
  account's `gh` login (`POST /repos/<owner>/<repo>/actions/runners/registration-token`),
  keeps it in a `no_log` task's memory and the registering command's
  environment only, and leaves a directory that already has a `.runner` file
  alone. The login needs admin on each repository and the `repo` scope:
  `gh auth refresh --scopes repo` once over `ssh <alias>`, then drop it again
  if you want the narrower token back after the first run.
- **Logs:** `~/.cache/dotfiles-runner-<owner>-<repo>.{out,err}` (cron's own
  mail for the account is empty unless a job line breaks).

## PostgreSQL

The play (`roles/osx/tasks/offload-postgres.yml`) gives the work account a
PostgreSQL 16 server for test suites run on the Mac. Same posture as the
runners: nothing uses sudo or the owner's Homebrew, and nothing touches the
owner's account or settings.

- **Install.** `postgres` is pinned in `roles/osx/files/mise-offload/offload.toml`
  beside the other tools; mise's postgres plugin compiles it from source, so
  the Command Line Tools must be present. `POSTGRES_CONFIGURE_OPTIONS` in that
  file builds without icu, readline and openssl (the plugin's defaults would
  reach into the owner's Homebrew), and with no uuid support: a localhost test
  server needs none, `psql` simply has no line editing, and there are no
  TLS connections. The pinned minor is a reviewed bump.
- **Data and access.** The cluster is `osx_postgres_data` (default
  `~/postgresql-16`), initialised by `initdb` only when that directory has no
  `PG_VERSION`, with `--auth-local=peer --auth-host=scram-sha-256`. The server
  listens on `localhost` and on a Unix socket in `osx_postgres_socket_dir`
  (default `~/postgresql-16-run`, mode 0700, socket mode 0700), so another
  account on the Mac reaches neither. The `fleet` role is the cluster's
  bootstrap superuser, and the gate creates `osx_postgres_role` with
  `createuser -s` only when it is missing, so it covers any database a suite
  creates.
- **Password.** The play appends `localhost:<port>:*:fleet:<password>` to
  `~/.pgpass` (mode 0600), a random password, only while no such line exists,
  and never prints it (`no_log`). The gate sets it on the role with `ALTER ROLE`
  over a peer connection on each start, from the file, feeding the statement
  on stdin so no process list shows it. Nothing writes it anywhere shared or
  tracked.
- **Connecting.** Port 5432 (`osx_postgres_port`). The local mode needs no
  password: a suite that takes `POSTGRES_SOCKET_DIR` connects over the socket
  with peer auth, `POSTGRES_SOCKET_DIR=$HOME/postgresql-16-run`. Over TCP,
  `psql -h localhost` reads `~/.pgpass`; a suite that does not read it needs
  `POSTGRES_USER` (default `fleet`) and `POSTGRES_PASSWORD`, exported in the
  session from the file, not stored:

  ```zsh
  export POSTGRES_PASSWORD="$(awk -F: '$1=="localhost" && $4=="fleet" {print $5; exit}' ~/.pgpass)"
  ```

  (a password with a `\` or `:` is escaped in the file, but the generated ones
  hold neither).
- **Connections.** `max_connections` is `osx_postgres_max_connections`: a test
  pool is two connections per scheduler per partition, so it is the Mac's
  cores times two times `osx_postgres_partitions` (default 4) plus 50, and
  never below PostgreSQL's 100. Raise the partitions for a wider run.
- **Keeping it running.** Like the runners: an `@reboot` crontab line and one
  every `osx_runner_recheck_minutes`, both calling `runner-start.sh` (the
  runners' starter, told by `RUNNER_GATE` and `RUNNER_PID_PREFIX` to run
  `postgres-gate.sh` and keep its pid, lock and logs as
  `~/.cache/dotfiles-postgres-<dir>.*`). It starts the gate detached at nice
  10 and does nothing when it already runs. The server log is
  `<data dir>/server.log`. To stop it for good, remove the two `dotfiles
  postgres` crontab lines, then kill the pid in the pid file; the gate stops
  the server fast on `TERM`.
- **Yielding.** `postgres-gate.sh` starts the server only when
  `runner-gate.sh`'s `mac_is_free` holds: input idle for
  `osx_runner_idle_seconds` and the one-minute load under
  `osx_runner_load_max`. Once input arrives, within that window, it runs
  `pg_ctl stop -m fast`: sessions are disconnected, their open transactions
  rolled back, committed data flushed, nothing killed mid-write, so a test run
  in flight fails and is re-run. It starts again on the next idle check
  (every ten seconds). Load alone never stops it: a test run loads the Mac
  through the server it uses, and stopping on that would end every busy run.
  The runner's rule is the opposite on this point (a running job is left to
  finish), by the owner's priority over a job that can be rerun.
