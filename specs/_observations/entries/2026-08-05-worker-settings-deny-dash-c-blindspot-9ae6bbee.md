- 2026-08-05 [dotfiles] SECURITY: planwright config/worker-settings.json deny rules are all `git <subcommand>` prefixes (git push --force, git merge, git commit --amend, git reset --hard, git filter-branch), so none of them match the `git -C <path> <subcommand>` spelling. A worker running `git -C /path push --force` evades every force-push, merge, amend and reset guardrail in the fragment while the deny block appears to protect them. Claude Code emits the -C spelling routinely when operating on a worktree, so this is a reachable shape, not a theoretical one. Any adopter who adds a broad Bash(git -C:*) allow to fix the matching gap on the allow side silently disables the entire deny block. Fix is to pair every deny with its `git -C * <sub>` twin.
