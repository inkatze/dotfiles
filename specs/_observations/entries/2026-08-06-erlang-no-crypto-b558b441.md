- 2026-08-06 [dotfiles] The mise-managed Erlang 28.3 on the Linux host is built without OpenSSL: its lib/ carries no `crypto` and no `ssl` application, so `crypto:strong_rand_bytes/1` is undefined. Consequences are broad, not cosmetic — `mix deps.get`, `Mix.install/1` and anything reaching hex.pm over TLS all fail, so no Elixir project on this host can resolve a dependency, and the repo declares erlang and elixir in roles/environments as if it could. It breaks the serving side too, not only the fetching side: a Phoenix or Cowboy endpoint cannot terminate HTTPS without `ssl`, which is the operator's stated end goal for this machine. Surfaced while executing specs/dev-services Task 4, whose Done-when needs the consuming stack Redis client run against a live server; that clause was answered by fetching and compiling the pinned library directly, which works but is a workaround. **Cause confirmed** (this entry originally said "likely"): the kerl build log at `~/.cache/mise/erlang/kerl/builds/28.3/otp_build_28.3.log` records `Probe failed for libssl-dev`, then `configure: WARNING: No (usable) OpenSSL found, skipping ssl, ssh and crypto applications`. Three applications, not two — `ssh` is skipped as well. Note it is a WARNING: the build then reports success, so mise installs a working-looking erlang and the breakage surfaces only at first use. `libssl3t64` (runtime) was already installed; only the headers were missing, the same runtime-vs-headers split that bit libyaml. Fix is to make the headers present and rebuild: `mise run linux` (libssl-dev is in `linux_apt_packages` as of the change that landed with this note), then `mise uninstall erlang@28.3 && mise install erlang@28.3`. Verify with `erl -noshell -eval 'io:format("~p~n",[crypto:strong_rand_bytes(4)]),halt().'` — a binary, not `undef`. Belongs to whichever bundle owns the environments role rather than to dev-services.
